Open Knowledge Format · v0.2

Conhecimento como markdown versionável, legível por gente e por agente.

OKF é um formato aberto e vendor-neutral: um bundle é uma árvore de arquivos .md com YAML frontmatter — sem SDK, sem API proprietária, sem lock-in.

Começar o guia Ler a SPEC
O que é

Um formato, não uma plataforma

O repositório knowledge-catalog gira em torno da especificação OKF. O agente de referência e o visualizador existem só para tornar o formato tangível nas duas pontas: quem produz e quem consome. Nada aqui é produto oficial do Google.

📄 Markdown + frontmatter

Cada conceito é um arquivo .md: YAML no topo para o que se filtra e indexa, corpo livre para a prosa, o schema e as queries que humanos e LLMs realmente leem.

🔀 Versionável em git

Um bundle é um diretório. Pull request, diff linha a linha, blame e review funcionam de graça — curar conhecimento vira atividade normal de engenharia.

🔓 Vendor-neutral

Qualquer um produz (humano, agente ADK/LangChain, export de Dataplex, Unity Catalog, Collibra) e qualquer um consome (Obsidian, MkDocs, um LLM, um índice de busca).

🧭 Divulgação progressiva

index.md por diretório deixa o agente navegar a hierarquia um nível por vez, em vez de carregar o bundle inteiro no contexto.

🕸️ Grafo, não só árvore

Links markdown normais entre conceitos expressam relações mais ricas do que o pai/filho implícito no diretório.

🔎 Confiança de primeira classe

v0.2 põe no frontmatter de onde veio (sources), quem produziu e conferiu (generated, verified) e se ainda vale (status, stale_after).

Formato

Bundle, conceito, frontmatter

Um bundle é a unidade de distribuição: uma árvore de diretórios organizada como o domínio pedir. Todo .md não-reservado é um conceito; o concept ID é o caminho do arquivo sem o .md. Só dois nomes são reservados: index.md (listagem do diretório) e log.md (histórico de atualizações).

Estrutura

O diretório é livre; a semântica vem do frontmatter e dos links.

# bundle
path/to/bundle/
  index.md            # listagem (opcional)
  log.md              # histórico (opcional)
  metrics/
    index.md
    gross-margin.md   # um conceito
  computations/
    revenue-ytd.md
  attesters/
    sql_equality.py

Um conceito

type é o único campo sempre obrigatório — um doc só com type já é conformante.

---
type: BigQuery Table
title: events_
description: Eventos GA4 particionados por dia.
resource: bigquery://project/dataset/events_
tags: [ga4, ecommerce]
status: stable
---

# Schema
...prosa, tabelas, queries de exemplo...

Campos do frontmatter

FamíliaCamposPara quê
Identidadetype (obrigatório), title, description, resource, tagsRoteamento, filtro e apresentação. Tipos não são registrados centralmente; consumidores toleram tipos desconhecidos.
Proveniênciasources (com author, usage_count, last_modified, usage_window)De onde a afirmação veio. OKF registra os sinais de credibilidade, não um veredito.
Confiançagenerated, verifiedQuem produziu e quem confirmou. Daí o consumidor deriva a trust tier: não verificado, confirmado por máquina, revisado por humano.
Ciclo de vidastatus (draft/stable/deprecated), stale_afterSe o conceito ainda está atual. Ausente status ⇒ stable.
Computaçãoruntime, parameters, computation, executor, attesterSó no tipo Attested Computation (§10).

Produtores podem incluir quaisquer chaves extras; consumidores devem preservar chaves desconhecidas e não podem rejeitar um bundle por campo opcional ausente, tipo desconhecido, link quebrado ou index.md faltando.

🧾 Attested Computation — a novidade da v0.2

Proveniência responde “de onde veio esse número”; atestação responde “ele foi produzido do jeito que mandamos?”. Uma computação sancionada vira um conceito próprio (type: Attested Computation) com runtime (bigquery, dbt, python, Looker…) definindo o que os parameters significam, um executor que roda e devolve um receipt, e um attester — código determinístico, sem LLM — que inspeciona o receipt e dá o veredito. Métrica, dashboard e relatório apenas linkam para ela. OKF guarda a computação e o meio de checá-la; não executa nada.

Como funciona

Do dataset ao bundle navegável

O agente de referência (Python, Google ADK + Gemini) roda em duas passadas e escreve markdown puro. O visualizador lê esse mesmo markdown — produtor e consumidor conversam só por arquivos.

BigQuery→ Passada BQ · 1 doc por conceito→ Passada web · crawl dos seeds→ Bundle OKF (.md)→ viz.html

1 · Passada BQ

Escreve um doc OKF por conceito que a fonte anuncia, usando só metadados do BigQuery.

2 · Passada web

O LLM vira crawler: busca os seeds via fetch_url, decide quais links seguir e, por página, enriquece conceitos existentes, cria um references/<slug> ou pula. Teto duro de páginas (--web-max-pages) e filtro de hosts são impostos dentro da ferramenta.

3 · Consumo

visualize gera um HTML self-contained: grafo force-directed, painel de detalhe com o markdown renderizado, backlinks “Cited by”, busca e filtro por tipo.

Pré-requisitos

O que precisa estar no lugar

Só para rodar o agente de referência. Para ler ou escrever OKF à mão, nada disso é necessário — é markdown.

Python 3.11+

O pacote reference-agent vive em okf/ e instala em venv.

python3.13 -m venv .venv

BigQuery

Datasets públicos são legíveis, mas os bytes lidos são cobrados no seu projeto.

gcloud auth application-default login
gcloud config set project <id>

Gemini

Via AI Studio ou Vertex AI.

export GEMINI_API_KEY=...
# ou Vertex:
export GOOGLE_GENAI_USE_VERTEXAI=true
export GOOGLE_CLOUD_PROJECT=<id>
export GOOGLE_CLOUD_LOCATION=<region>
Guia de uso · passo a passo

Produzir e consumir um bundle

Todos os comandos rodam a partir da pasta okf/ do repositório.

1

Instalar

Cria o venv e instala o pacote em modo editável, com as dependências de dev.

python3.13 -m venv .venv
.venv/bin/pip install --index-url https://pypi.org/simple/ -e .[dev]
2

Gerar um bundle a partir de um dataset

Aponte para um dataset BigQuery e uma pasta de saída. Os seeds da passada web são explícitos.

.venv/bin/python -m reference_agent enrich \
    --source bq \
    --dataset <project>.<dataset> \
    --web-seed-file <path/to/seeds.txt> \
    --out ./bundles/<name>
3

Rodar só o BigQuery, sem web

Omita os seeds ou passe --no-web para pular a passada de crawl.

.venv/bin/python -m reference_agent enrich \
    --source bq --dataset <project>.<dataset> \
    --no-web --out ./bundles/<name>
4

Iterar em um conceito só

--concept é repetível — útil para refinar um doc sem regerar o bundle inteiro.

.venv/bin/python -m reference_agent enrich ... \
    --concept tables/events_
5

Visualizar o bundle

Gera bundles/<name>/viz.html: um arquivo só, sem backend, para abrir no navegador, versionar ao lado do bundle ou servir estático.

.venv/bin/python -m reference_agent visualize --bundle ./bundles/<name>

# saída em outro lugar, com outro título no header
.venv/bin/python -m reference_agent visualize \
    --bundle ./bundles/crypto_bitcoin \
    --out /tmp/btc.html --name "Bitcoin OKF"
6

Rodar os testes

Suíte pytest do pacote de referência.

.venv/bin/pytest
Bundles & toolbox

OKF na prática

Cada sample em okf/samples/ traz a receita (seeds + comando enrich exato) e o bundle produzido, versionado em okf/bundles/ com o viz.html ao lado.

🛒 ga4

GA4 Google Merchandise Store — dataset público de e-commerce, semeado com a documentação canônica do GA4 BigQuery Export.

💬 stackoverflow

Espelho do Stack Exchange Data Dump. Exercita enriquecimento multi-conceito a partir de páginas de doc transversais.

₿ crypto_bitcoin

Blocos, transações, inputs e outputs do pipeline bitcoin-etl. Exercita relações de chave estrangeira descritas em prosa.

🏪 acme_retail

Bundle sintético que demonstra a v0.2 completa: computations/, attesters/ (Python determinístico), métricas, políticas e skills.

🧰 toolbox/mdcode — Metadata as Code

Gerencia metadados como artefatos de código sincronizáveis com o Knowledge Catalog: snapshot com manifesto, arquivos YAML por entrada, e os comandos init / pull / push (BigQuery e knowledge bases).

🤖 toolbox/enrichment — Enrichment Agent

Agente TypeScript pronto para uso, mais um harness customizável, para produzir, evoluir e manter metadados no Knowledge Catalog e deixá-los prontos para consumo por agentes.

Versões

De v0.1 a v0.2

A v0.2 é quase toda aditiva: chaves opcionais novas, um tipo de conceito novo e um heading convencional novo. Na ausência de todos eles, o documento é um conceito v0.1 comum.

v0.1
O núcleoEstrutura de bundle, nomes reservados, type obrigatório, title/description/resource/tags, cross-linking, index, log e conformance permissiva.
v0.2 ➕
Proveniência, confiança e ciclo de vidasources com sinais de credibilidade por fonte, generated, verified, status, stale_after, e a convenção de ator (<produtor>/<versão>, human:<id>, process:<id>).
v0.2 ➕
Attested ComputationTipo novo com runtime, parameters, computation, executor e attester, mais o heading de corpo # Computation.
Fora do escopo
O que OKF não fazNão define taxonomia fixa de tipos, não prescreve infraestrutura de armazenamento ou consulta, não substitui schemas de domínio (Avro, Protobuf, OpenAPI — só os referencia) e não padroniza o empacotamento do código que executor e attester apontam.
